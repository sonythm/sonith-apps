Reuse context and share it with your team: a practical playbook

How to turn what you taught Claude into something the whole team shares: CLAUDE.md in git, project skills, shared connections, plugins, Projects, plus a cheat sheet for choosing the right tool.

  • Put shared instructions, skills and settings in the repository
  • Never share keys or personal data, even in a private repo
  • Use the cheat sheet to pick the right tool for each job

Reading level

Teaching Claude something once is good. Teaching it once for the whole team is better. Everything a teammate would otherwise have to explain to Claude again (how we build, how we write, which tools we use) can be written down and shared. This part is a practical playbook, with a cheat sheet picture to choose the right tool. Facts come from Anthropic's Claude Code and support documentation, checked on 2026-10-21; where availability depends on your plan, check your plan.

The idea: write it down where everyone gets it

In plain words

If a good habit lives only in one person's head or chat history, it leaves when they do. If it lives in the project folder, every teammate (and every new session) gets it automatically.

What to share, and where it lives

WhatWhere it lives (as documented)How the team gets it
Instructions and rules./CLAUDE.md or ./.claude/CLAUDE.md, plus .claude/rules/Commit to the repository
Reusable know-how.claude/skills/<name>/SKILL.mdCommit to the repository
Specialised helpers.claude/agents/ (subagents)Commit to the repository
Connections to tools.mcp.json at the project rootCommit it; Claude Code asks for approval before using project servers
Settings, plugins.claude/settings.jsonCommit it; each person still installs plugins on their own machine
Expert viewDetails behind the table

Anthropic's memory page says project instructions are "shared with your team through version control", while CLAUDE.local.md holds personal project preferences and should be added to .gitignore. For skills, the Claude Code docs say to commit .claude/skills/ to share. Subagent files are Markdown with YAML frontmatter, and the docs say to commit .claude/agents/ so teammates get the same subagents. For MCP, project scope stores servers in a .mcp.json file at the project root; the docs say Claude Code prompts for approval before using project-scoped servers in interactive sessions, and that ${VAR} and ${VAR:-default} expansion lets teams share configuration while keeping machine-specific paths and API keys out of the file.

Step by step: a shared setup

Expert viewPlugins and marketplaces

Anthropic describes a plugin as a directory of skills, agents, hooks and MCP servers that Claude Code installs as one unit, usually with a manifest at .claude-plugin/plugin.json. A marketplace is a catalog (a repository or directory with a .claude-plugin/marketplace.json file) that lists plugins; you add a marketplace once and install plugins by name, using /plugin in a session. Install scopes are user, project (enabled for everyone in the repository through the committed .claude/settings.json, though each collaborator installs it on their own machine) and local. Plugin skills are namespaced, such as /my-plugin:review.

Through managed settings an organisation can allowlist or block marketplaces and force-install plugins. A plugin runs code with your user privileges, so Anthropic's documentation points to its plugin security page for what to review first. An enabled plugin also adds its skill and agent descriptions to context on every turn, so measure what each one costs.

Sharing in the Claude app: Projects

For people who work in the chat app rather than a code editor, Projects are the shared workspace.

Expert viewRoles and limits

Anthropic's support article says members can have view-only or edit access, and editors can change instructions and knowledge, add or remove members and contribute actively. Chats inside a project do not share context unless the information is in the knowledge base. Anthropic's skills documentation says custom skills in claude.ai are individual and cannot be centrally managed by admins, so for team-wide skills use Claude Code (repository or plugin) or the API (workspace-wide). Availability varies by plan, so check your plan.

Habits that keep a shared setup healthy

Careful

What never to share: passwords, API keys, tokens, customer data or anyone's personal details. Not in CLAUDE.md, not in a skill, not in .mcp.json (use environment variable expansion), not in a Project's knowledge. Treat a private repository as shared with more people than you think.

Real example

A team keeps three lines in CLAUDE.md (build command, test command, "never edit /generated"), a /release-notes skill that formats changelogs the same way every time, and a project-scoped .mcp.json for their issue tracker. A new teammate clones the repository, and Claude already knows how this team works.

If it is worth teaching Claude twice, it is worth committing once.

Glossary
Repository
The shared folder, tracked by version control, that holds a project's files.
Version control
A system (such as git) that records changes so teams can share and review them.
Plugin
A package of skills, agents, hooks and MCP servers installed as one unit.
Marketplace
A catalog that lists plugins and where to fetch each one.
Managed settings
Organisation-wide configuration deployed by administrators.
Project (app)
A shared workspace in the Claude app with instructions and knowledge files.

Frequently asked questions

Can I share skills with colleagues who use only the chat app?

Not centrally. Anthropic says custom skills in claude.ai are individual to each user, so each person uploads their own. Projects are the shared option there.

Is a private repository safe for secrets?

No. Keep secrets out of the repository and use environment variables or a secrets manager.

How do I stop a teammate's private preferences leaking into the shared file?

Put them in CLAUDE.local.md (kept out of git) or ~/.claude/CLAUDE.md.

Key takeaways

  • Put shared instructions, skills and settings in the repository
  • Never share keys or personal data, even in a private repo
  • Use the cheat sheet to pick the right tool for each job
