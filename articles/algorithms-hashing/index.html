Hashing and hash tables

How a hash function turns a key into a bucket number so lookups take about one step on average, what collisions are, how tables grow, and why password hashing is a different job.

  • Hash tables for data and password hashing are different jobs

Reading level

A hash table lets you find something by name in about one step, however many things are stored. That sounds like magic, and the trick behind it is surprisingly simple. This part uses a coat-check picture, an animation with a collision, and an Expert view on the details that make hash tables work and sometimes fail.

The coat-check picture

At a coat check, you hand over a coat and get a numbered ticket. Later the ticket tells staff exactly which hook to go to, with no searching along the rail.

In plain words

The key is what you look things up by, such as a word or a name. The hash function turns the key into a number. That number says which bucket (hook) to look in. Nobody scans the whole rail.

Expert viewDefinitions

A hash table stores key-value pairs in an array of buckets. A hash function maps a key to an integer; the table reduces that integer to a valid bucket index, often by taking the remainder after dividing by the number of buckets. A good function is deterministic (the same key always gives the same number) and spreads keys evenly. Lookup, insert and delete all start by hashing the key.

Watch it work

In plain words

Sometimes two different keys get the same bucket number, like two people given the same hook. That is a collision. It is normal and every hash table has a plan for it.

Expert viewWhy collisions are unavoidable

There are far more possible keys than buckets, so by the pigeonhole principle some keys must share a bucket. Even with few keys, collisions appear sooner than intuition suggests: the birthday problem shows that among only 23 people, two share a birthday with probability a little over one half. So a design must assume collisions and handle them efficiently.

Handling collisions

In plain words

Chaining is like several coats on one hook. Open addressing is like moving to the next empty hook. In both cases, finding a coat still means looking at only a few places.

Expert viewChaining and open addressing compared

With chaining, each bucket stores a collection (often a linked list), and a lookup compares keys along that chain. With open addressing, every item sits directly in the array; a collision triggers probing, such as stepping to the next slot (linear probing) or following another deterministic sequence. Deleting under open addressing needs care, because simply emptying a slot can break the probe path of other items, so a marker is usually left behind. Open addressing keeps data compact, but its performance degrades sharply as the table fills.

Load factor and resizing

In plain words

When hooks get crowded, staff add more hooks and re-sort the coats. It takes a while once, then everything is quick again.

Expert viewLoad factor and amortised cost

The load factor is the number of stored items divided by the number of buckets. Tables keep it below a chosen limit by growing when it is exceeded. Growing means creating a larger array and re-inserting every item, which is O(n) for that one insert. If the size grows by a constant factor such as doubling, the cost spread over all the inserts is constant per insert, so inserts are amortised O(1). Where a table must never pause, some designs spread the re-hashing over many operations.

Expert viewAverage versus worst case

The O(1) average assumes a good hash function and a bounded load factor, so each bucket holds only a few items. The worst case is O(n): if every key lands in one bucket, a lookup is a linear scan of everything. (Some designs reduce the chain cost, for example by storing long chains in a balanced structure, but that is an implementation choice and not part of the basic idea.) Hash tables also do not keep keys in sorted order, so "give me the smallest key" or "all keys from A to F" is not what they are for.

Where hashing is used

Real example

Counting words in a book: for each word, find its entry in a hash table and add one. A book of 100,000 words is done in about 100,000 steps, not 100,000 times the number of different words.

Hashing also appears in checksums: a fast hash of a file or message is recomputed later to check that nothing was corrupted by accident.

A different job: passwords

Careful

Hashing for passwords is a different job from hashing for tables. Never store passwords with a fast general-purpose hash. Use a dedicated, deliberately slow password-hashing function from a vetted library, with a unique random salt for each user, and follow the library's current guidance on settings. Do not write your own.

Expert viewGood hash functions, and which kind to use

For tables, a good function is deterministic, fast, and uniform: each bucket should be about equally likely, and small changes in a key should scatter the results. It must also agree with equality: keys that are equal must give equal hashes.

Non-cryptographic hashes are built for speed and spread, and suit tables and checksums. Cryptographic hashes add security goals, such as being infeasible to reverse or to find two inputs with the same output. Password storage needs more again: a hash that is slow and expensive to compute, designed to resist guessing at scale, plus a salt to defeat precomputed lists. A fast cryptographic hash is still the wrong tool for passwords.

Expert viewHash-flooding attacks

If an attacker knows the hash function and can choose the keys (for example, names in a web request), they can pick many keys that all collide, forcing the table into its O(n) worst case and making each operation slow. Common defences in general terms: use a hash function with a secret random seed chosen at start-up, limit input sizes, or use a table design that bounds the damage of long chains. This is one more reason not to invent your own hash for untrusted input.

Try it by hand

A hash table trades a little memory and a good hash function for lookups in about one step.

Glossary
Hash function
Turns a key into a number.
Hash table
A structure that stores items in buckets chosen by hashing the key.
Bucket
One slot in the table that can hold an item or several.
Collision
Two keys that map to the same bucket.
Chaining
Each bucket keeps a list of its items.
Open addressing
Collisions are resolved by probing for another slot.
Load factor
Items divided by buckets.
Salt
Random data added to a password before hashing, unique per user.
Checksum
A small value used to detect accidental changes in data.

Frequently asked questions

Is a hash table always O(1)?

Only on average, with a good hash function and a controlled load factor. The worst case is O(n).

Can two different keys have the same hash?

Yes. That is a collision, and tables are designed to cope with it.

Can I get the original key back from the hash?

A table does not need to, because it stores the key. For security hashes, being hard to reverse is a design goal.

Can I store passwords with a fast hash and a salt?

No. Use a dedicated slow password-hashing function from a vetted library.
