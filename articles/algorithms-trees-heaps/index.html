Trees and heaps

How trees organise data like a family tree, how a binary search tree finds things quickly, and how a heap always hands you the most urgent item first.

  • A tree stores items in parent and child links, so each step can rule out half the data
  • A binary search tree is fast only while it stays balanced
  • A heap keeps the smallest or most urgent item at the top for quick access

Reading level

Many things in computing are shaped like trees: folders inside folders, the structure of a web page, the choices in a game. A tree is a simple idea with a big payoff: if data is arranged the right way, you can find an item without looking at most of the others. This part starts with the family-tree picture, then meets two useful tree-based structures: the binary search tree and the heap. Each section has a plain layer first and an Expert view after it.

What a tree is

In plain words

Think of a family tree. At the top is one ancestor. Each person has children, and each child has their own children. Nobody has two parents inside the tree, and there are no loops. A computing tree works the same way, with items instead of people.

Expert viewTrees as a data structure

A tree is a connected graph with no cycles. In a rooted tree, every node except the root has exactly one parent. The depth of a node is the number of edges from the root, and the height of the tree is the greatest depth. A binary tree allows at most two children per node, called left and right. The number of nodes at each level can at most double as you go down, so a binary tree holding n items can be as short as about log base 2 of n levels. That shortness is the source of the speed in the next section.

Binary search tree: ask one question per level

In plain words

A binary search tree keeps one rule at every item: smaller values go to the left, bigger values go to the right. To find a number, start at the top and ask: is mine smaller or bigger? Go left or right, and you have just ignored half of what remains. It is like guessing a number between 1 and 100 by asking "higher or lower?".

Inserting works the same way: follow the left and right choices until you reach an empty spot, and hang the new item there.

Expert viewBalance and cost

Search, insert and delete on a binary search tree take time proportional to its height. When the tree is balanced the height is about log n, so these are O(log n). When it is lopsided, for example after inserting already sorted values into a plain tree, the height can reach n and the cost becomes O(n). Space is O(n).

Self-balancing variants exist that keep the height close to log n by rearranging the tree (called rotations) during inserts and deletes. Well-known families include AVL trees and red-black trees; I name them only as examples of the idea. Databases and file systems often use a related, wider kind of tree (a B-tree) that stores many items per node to reduce slow disk reads.

Walking a tree

Sometimes you want to visit every item, not find one. A tree walk (traversal) visits each node once. The usual recursive form for a binary tree has three versions that differ only in when the node itself is handled.

Key idea

An in-order walk of a binary search tree visits the items in sorted order, from smallest to largest. This is a free sort: the structure already holds the order.

Expert viewTraversal notes

All three depth-first walks take O(n) time because each node is visited once, and use stack space proportional to the height (O(log n) when balanced, O(n) when lopsided). A level-order walk, visiting the tree one level at a time, uses a queue instead and is the same idea as breadth-first search from the graph part of this series. Pre-order is handy for copying a tree, post-order for deleting one safely (children before parents).

Priority queues and the hospital waiting room

In plain words

In a hospital waiting room, people are not seen in the order they arrive. The most urgent patient goes first, and if a more urgent patient walks in, they jump ahead. A priority queue works like that: you can add items at any time, and you can always ask for the most urgent one.

Keeping a fully sorted list would work but is wasteful, since you only ever need the top item. A heap is a tree built for exactly this job. In a min-heap, every parent is smaller than or equal to its children, so the smallest item is always at the root. (A max-heap is the mirror image.) Note this is a weaker rule than a search tree: a heap does not keep left and right sides in order.

How a heap works

To insert, place the new item in the next free spot at the bottom, then compare it with its parent. If it is smaller, swap, and repeat. This "sifting up" stops quickly because the tree is short.

To extract the smallest, take the root, move the last item of the tree into the root's place, then "sift down": compare it with its two children and swap it with the smaller child, repeating until it is no larger than both children. The heap rule is restored.

Expert viewHeap in an array

A heap is a complete binary tree: every level is full except possibly the last, which fills from the left. That shape lets it live in a plain array with no pointers. With zero-based indexes, the node at index i has its parent at index (i - 1) / 2 (rounded down) and its children at 2i + 1 and 2i + 2.

OperationTime
Peek at the minimumO(1)
InsertO(log n)
Extract minimumO(log n)
Build a heap from n itemsO(n)
Search for an arbitrary valueO(n)

Building from n items in O(n) uses a bottom-up method: sift down each non-leaf node starting from the last. Most nodes are near the bottom and move only a short way, which sums to linear work, better than n separate inserts at O(n log n). A heap does not support fast arbitrary search, which is why it is a priority queue and not a general lookup structure.

Where you meet them

Real example

To find the 3 largest numbers in a huge stream, keep a small min-heap of size 3. For each new number, if it beats the smallest in the heap, swap it in. You never store the whole stream.

Try it by hand

On paper, insert 7, 3, 9, 1 into an empty binary search tree, in that order.

Then try inserting 1, 3, 7, 9 in that order instead and see what shape you get.

A tree is fast when each step lets you ignore half of what is left.

Glossary
Tree
Items linked as parents and children with no loops.
Root
The top item of a tree.
Leaf
An item with no children.
Binary search tree
A binary tree where smaller values go left and bigger values go right.
Balanced
A tree whose height stays close to log n.
Traversal
Visiting every item of a tree once.
Priority queue
A collection where you always take out the most urgent item.
Heap
A tree-shaped structure that keeps the smallest (or largest) item at the top.
Sift
Swap an item up or down the heap until the heap rule holds.

Frequently asked questions

Is a heap the same as a binary search tree?

No. A heap only guarantees that each parent is smaller than its children, so it finds the minimum fast but cannot search for an arbitrary value fast.

Why does the order of insertion matter for a search tree?

Without rebalancing, sorted input produces a long chain, and searches become as slow as scanning a list.

Why store a heap in an array?

Its complete shape makes parents and children computable from the index, so no pointers are needed.

Are folders on a computer really a tree?

Yes. Each folder has one parent folder and can hold many children, which is the shape of a rooted tree.

Key takeaways

  • A tree stores items in parent and child links, so each step can rule out half the data
  • A binary search tree is fast only while it stays balanced
  • A heap keeps the smallest or most urgent item at the top for quick access
