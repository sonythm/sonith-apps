Clean Architecture in .NET Core, explained simply

A kitchen analogy for layers, the one rule that makes the design work, a small C# example, what it does for testing, common mistakes, and when not to use it.

  • Business rules go in the centre
  • Dependencies point inward only
  • Use it when complexity justifies it, not by default

Reading level

Software that works on day one often becomes painful by year two. Changing one thing breaks three others. Tests are slow because everything needs a database. Switching a tool means rewriting half the code. Clean Architecture is a way of organising code to avoid that pain. This article explains it for beginners, with .NET Core (the modern, cross-platform .NET) as the example. Each section gives you a plain picture first, then an Expert view with the precise terms.

The kitchen analogy

Picture a restaurant. The recipes are the heart of the business. The kitchen routine organises the work. The equipment and suppliers are the stove, fridge and delivery vans. The dining room is where customers meet the restaurant.

In plain words

If the stove breaks and you buy another brand, the recipes do not change. If the dining room is redecorated, the recipes do not change. But if the recipes change, everything around them may need to adapt. Clean Architecture arranges software the same way.

Expert viewWhere the idea comes from

The approach goes by several names that overlap strongly: Clean Architecture, Hexagonal Architecture (ports and adapters) and Onion Architecture. They share the same core principle: the business logic sits in the middle and does not depend on delivery mechanisms such as the web framework, the database or the user interface. Names and exact layer counts vary between authors; the dependency rule is what matters.

The layers

The one rule that matters

Source code dependencies point inward only. Outer layers know about inner layers, never the reverse.

How can the application use a database without knowing about it? Through an interface, a promise written in code. The application layer says: "I need something that can save an order." The infrastructure layer provides it.

Expert viewThe dependency rule, precisely

Dependency inversion means the high-level policy (application and domain) owns the abstraction, and the low-level detail (database, web) implements it. In ports-and-adapters vocabulary, IOrderRepository is a port and its Entity Framework Core implementation is an adapter. In .NET, the built-in dependency injection container in ASP.NET Core connects them at start-up, usually in the composition root of the outermost project.

A compile-time guarantee helps: project references enforce the rule, so Domain references nothing, Application references Domain, and Infrastructure and the web project reference Application. If someone calls the database from the domain project, it will not compile.

What it looks like in a .NET solution

Text
Shop.sln
  src/
    Shop.Domain          // entities, value objects, business rules
    Shop.Application     // use cases, interfaces (IOrderRepository)
    Shop.Infrastructure  // EF Core, email, payment adapters
    Shop.WebApi          // ASP.NET Core controllers or endpoints
  tests/
    Shop.Domain.Tests
    Shop.Application.Tests

A small example

The domain protects its own rules:

C#
// Shop.Domain
public class Order
{
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyList<OrderLine> Lines => _lines;

    public void AddLine(string product, int quantity, decimal unitPrice)
    {
        if (quantity <= 0)
            throw new ArgumentException("Quantity must be positive.");
        _lines.Add(new OrderLine(product, quantity, unitPrice));
    }

    public decimal Total() => _lines.Sum(l => l.Quantity * l.UnitPrice);
}

The application layer defines what it needs and runs the use case:

C#
// Shop.Application
public interface IOrderRepository
{
    Task SaveAsync(Order order);
}

public class PlaceOrderHandler
{
    private readonly IOrderRepository _orders;
    public PlaceOrderHandler(IOrderRepository orders) => _orders = orders;

    public async Task<decimal> HandleAsync(PlaceOrder command)
    {
        var order = new Order();
        foreach (var l in command.Lines)
            order.AddLine(l.Product, l.Quantity, l.UnitPrice);
        await _orders.SaveAsync(order);
        return order.Total();
    }
}

Infrastructure then provides the real IOrderRepository, for example with Entity Framework Core and a SQL database. The names above are illustrative, not a framework you must install.

Expert viewDesign notes an experienced reviewer would raise
  • Rich domain, not anaemic. Rules live on the entity (AddLine validates) instead of in service classes that manipulate bags of properties.
  • Mapping lives at the boundaries. Convert between persistence models, domain models and API contracts in the outer layers so inner layers never depend on serialisation or ORM attributes.
  • Use cases as the unit of change. Whether you use plain handler classes or a mediator library is a style choice, not part of the architecture itself.
  • Money and units. Using decimal for currency, or a dedicated value object, avoids floating-point surprises; the domain is the right home for such rules.
  • Transactions at the use-case edge. A use case usually corresponds to one unit of work; keep transaction handling out of the domain.

Why it helps with testing

Because the domain and application layers do not touch a database, you can test them in milliseconds.

In plain words

Because the recipes do not depend on the stove, you can check the recipes without lighting a fire.

Expert viewA test in practice

A unit test of PlaceOrderHandler passes a fake IOrderRepository (an in-memory list or a mocking library), calls HandleAsync, and asserts on the returned total and on what the fake received. Domain tests need no fake at all: construct an Order, call AddLine with a zero quantity and assert that it throws. Reserve a smaller number of integration tests for the infrastructure adapters, run against a real or containerised database, to prove the mapping works.

Common mistakes

  1. Leaking the database into the domain. ORM attributes or database types in domain classes tie the heart to the equipment.
  2. An anaemic domain. Entities that are bags of properties while all rules live in services.
  3. Returning database entities from the API. Return purpose-built response objects.
  4. Skipping tests. The structure makes testing easy. Use it.

When not to use it

Careful

Clean Architecture has a cost: more projects, more files, more concepts to learn. For a small CRUD app (create, read, update, delete with little business logic), a quick prototype, a one-off script or a short-lived tool, it can be more ceremony than value.

Expert viewEvolving into it

A pragmatic path is a modular monolith: begin with feature folders in one project and extract the domain and application code into their own projects once rules and team size justify it. Keep the dependency direction right from the start (no domain code referencing the database), and the later split is mostly moving files. Avoid copying a template of many projects into a project that has only simple data entry.

Glossary
Domain
The part of the software that models the real business, with its concepts and rules.
Use case
One thing a user wants to do, such as placing an order.
Dependency inversion
The inner layer defines an interface, and the outer layer implements it.
Dependency injection
Handing a class the things it needs instead of letting it create them.
Port and adapter
The interface (port) and the code that implements it for a specific technology (adapter).
ORM
A library such as Entity Framework Core that maps code objects to database tables.
Entity
A domain object with an identity, such as an Order.
Repository
A class that saves and loads domain objects.

Frequently asked questions

Is Clean Architecture a framework I install?

No. It is a way of arranging your own code. You can do it with plain .NET projects.

Does it only work with .NET?

No. The idea is language-neutral. This article uses C# as the example.

Is it slower at run time?

The extra layers cost almost nothing at run time. The real cost is development effort and complexity.

How many layers must I have?

Three or four is typical. What matters is the dependency rule, not the count.

Key takeaways

  • Business rules go in the centre
  • Dependencies point inward only
  • Use it when complexity justifies it, not by default
