Clean Architecture in .NET Core, explained simply

A kitchen analogy for layers, the one rule that makes the design work, a small C# example, what it does for testing, common mistakes, and when not to use it.

Software that works on day one often becomes painful by year two. Changing one thing breaks three others. Tests are slow because everything needs a database. Switching a tool means rewriting half the code. Clean Architecture is a way of organising code to avoid that pain. This article explains it for beginners, with .NET Core (the modern, cross-platform .NET) as the example.

The kitchen analogy

Picture a restaurant. The recipes are the heart of the business: how to make the signature dish. The kitchen routine organises the work: take an order, check ingredients, cook, plate. The equipment and suppliers are the stove, the fridge and the delivery vans. The dining room is where customers meet the restaurant.

If the stove breaks and you buy another brand, the recipes do not change. If the dining room is redecorated, the recipes do not change. If you change supplier, the recipes still do not change. But if the recipes change, everything around them may need to adapt.

Clean Architecture says: arrange your software the same way. Keep the important business rules in the middle, and make everything else depend on them, never the other way around.

The layers

  • DomainThe heart. Business concepts and rules, written in plain C# with no database, no web and no frameworks. For a shop: an Order, a Customer, the rule that an order cannot be empty.
  • ApplicationThe use cases: "place an order", "cancel an order". It coordinates the domain objects and describes what it needs from the outside world through interfaces.
  • InfrastructureThe equipment: the database, email sending, file storage, payment services. It implements the interfaces the application layer described.
  • PresentationThe dining room: the web API, the website or the mobile app. It turns requests into use-case calls and results into responses.

The one rule that matters

Key idea

Source code dependencies point inward only. The domain knows nothing about the application. The application knows nothing about the database or the web. Outer layers know about inner layers, never the reverse.

How can the application use a database without knowing about it? Through an interface, a promise written in code. The application layer says: "I need something that can save an order." The infrastructure layer provides it. This trick is called dependency inversion.

What it looks like in a .NET solution

A typical solution has one project per layer:

Shop.sln
  src/
    Shop.Domain          // entities, value objects, business rules
    Shop.Application     // use cases, interfaces (IOrderRepository)
    Shop.Infrastructure  // EF Core, email, payment adapters
    Shop.WebApi          // ASP.NET Core controllers or endpoints
  tests/
    Shop.Domain.Tests
    Shop.Application.Tests

The project references enforce the rule: Domain references nothing, Application references Domain, Infrastructure and WebApi reference Application. If a developer tries to use the database from the domain project, it simply will not compile.

A small example

The domain protects its own rules:

// Shop.Domain
public class Order
{
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyList<OrderLine> Lines => _lines;

    public void AddLine(string product, int quantity, decimal unitPrice)
    {
        if (quantity <= 0)
            throw new ArgumentException("Quantity must be positive.");
        _lines.Add(new OrderLine(product, quantity, unitPrice));
    }

    public decimal Total() => _lines.Sum(l => l.Quantity * l.UnitPrice);
}

The application layer defines what it needs and runs the use case:

// Shop.Application
public interface IOrderRepository
{
    Task SaveAsync(Order order);
}

public class PlaceOrderHandler
{
    private readonly IOrderRepository _orders;
    public PlaceOrderHandler(IOrderRepository orders) => _orders = orders;

    public async Task<decimal> HandleAsync(PlaceOrder command)
    {
        var order = new Order();
        foreach (var l in command.Lines)
            order.AddLine(l.Product, l.Quantity, l.UnitPrice);
        await _orders.SaveAsync(order);
        return order.Total();
    }
}

Infrastructure then provides the real IOrderRepository, for example using Entity Framework Core and a SQL database, and the web layer registers it with the built-in dependency injection of ASP.NET Core. The names above are illustrative, not a framework you must install.

Why it helps with testing

Because the domain and application layers do not touch a database, you can test them in milliseconds. To test PlaceOrderHandler you give it a fake repository that simply remembers what it was given. No database, no network, no setup. Fast tests get run often, and tests that run often catch bugs early.

In plain words

Because the recipes do not depend on the stove, you can check the recipes without lighting a fire.

Other benefits

  • Replaceable parts. Changing the database or email provider touches only Infrastructure.
  • Clear homes for code. New team members know where things belong.
  • Business rules protected. The important logic cannot be accidentally mixed with screen code.
  • Longevity. The expensive part, the business logic, outlives technology trends.

Common mistakes

  1. Leaking the database into the domain. Using ORM attributes or database types in domain classes ties the heart to the equipment.
  2. An "anemic" domain. Entities that are bags of properties, while all rules live in service classes. Put rules where the data lives.
  3. Interfaces for everything. Not every class needs an interface. Create them where a layer boundary needs one.
  4. Over-layering. Adding five layers and a mapper for every field in a three-screen app.
  5. Returning database entities from the API. Return purpose-built response objects so the outside world does not depend on your internal shape.
  6. Skipping tests. The structure makes testing easy. Use it.

When not to use it

Careful

Clean Architecture has a cost: more projects, more files, more concepts to learn. For a small CRUD app (create, read, update, delete with little business logic), a quick prototype, a one-off script, or a short-lived tool, it can be more ceremony than value.

A good rule: start simple. Introduce the layers when business rules grow, when several people work on the code, or when you expect the system to live for years.

Where to go next

Look for the original idea (often called "Onion", "Hexagonal" or "Clean" architecture, the names vary slightly), read about domain-driven design for modelling the domain, and try the layout on a small project of your own.

Glossary
Domain
The part of the software that models the real business, with its concepts and rules.
Use case
One thing a user wants to do, such as placing an order.
Dependency inversion
The inner layer defines an interface, and the outer layer implements it.
Dependency injection
Handing a class the things it needs instead of letting it create them.
ORM
A library such as Entity Framework Core that maps code objects to database tables.
Entity
A domain object with an identity, such as an Order.
Repository
A class that saves and loads domain objects.

Frequently asked questions

Is Clean Architecture a framework I install?

No. It is a way of arranging your own code. You can do it with plain .NET projects.

Does it only work with .NET?

No. The idea is language-neutral. This article uses C# as the example.

Is it slower at run time?

The extra layers cost almost nothing at run time. The real cost is in development effort and complexity.

How many layers must I have?

Three or four is typical. What matters is the dependency rule, not the count.
