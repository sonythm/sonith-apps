Recursion and dynamic programming

How a problem that contains smaller copies of itself can be solved by recursion, why naive recursion can explode, and how remembering answers (dynamic programming) fixes it.

  • Recursion solves a problem by solving a smaller copy of it
  • Naive recursion can repeat the same work exponentially often
  • Dynamic programming stores sub-answers so each is computed once

Reading level

Some problems contain smaller copies of themselves. Open a Russian doll and there is a slightly smaller doll inside, then another, until the last one cannot be opened. That is recursion. It is a natural way to describe many solutions, but it has a trap: a careless version can do the same work millions of times. Dynamic programming is the cure, and it is one of the most useful ideas in algorithms. Each section has a plain picture and an Expert view.

Recursion: the Russian dolls

In plain words

To find out how many dolls are in a set, open the biggest. If it is empty, the answer is zero dolls inside. Otherwise the answer is one plus however many are inside the next doll. You keep asking the same question about a smaller doll, until you reach one you cannot open.

Every sound recursive solution has two parts:

  • Base case. The smallest version, answered directly. It stops the recursion.
  • Recursive case. Reduce the problem to a smaller one of the same kind, solve that, and combine.
Text
factorial(n):
    if n is 0: return 1              // base case
    return n times factorial(n - 1)  // recursive case

countdown(n):
    if n is 0: say "go"; return      // base case
    say n
    countdown(n - 1)                 // recursive case
Careful

Forget the base case, or take steps that never reach it, and the calls never stop. The program eventually runs out of stack space and fails.

Expert viewStack depth and tail calls

Each call that has not finished is kept on the call stack, so recursion to depth n uses O(n) stack space. Most languages cap that depth, so a very deep recursion can fail with a stack overflow even if the logic is right. A tail call is a recursive call that is the very last thing a function does; some language implementations can reuse the current stack frame for it, turning such recursion into a loop. Whether that happens depends on the language and its implementation, and many common languages do not guarantee it. Where depth could be large, rewrite as a loop or use an explicit stack.

The trap: naive Fibonacci

The Fibonacci numbers start 0, 1, 1, 2, 3, 5, 8 and each is the sum of the two before. The recursive definition is tempting:

Text
fib(n):
    if n is 0 or 1: return n
    return fib(n - 1) + fib(n - 2)
In plain words

Imagine asking two friends for answers, and each asks two more friends, and so on. Soon dozens of people are answering the identical question "what is fib(3)?" independently. Nobody wrote anything down.

Expert viewWhy it is exponential

The number of calls to compute fib(n) this way grows roughly like 1.618 to the power n (the golden ratio), which is exponential: adding one to n multiplies the work by about 1.6. The tree of calls is deep on the left (n levels) but contains only n + 1 distinct subproblems, fib(0) up to fib(n). The waste is repeated work on identical subproblems.

The fix: remember answers

Memoisation means storing each answer the first time you compute it, and looking it up afterwards.

Text
memo = empty table
fib(n):
    if n is 0 or 1: return n
    if n is in memo: return memo[n]
    memo[n] = fib(n - 1) + fib(n - 2)
    return memo[n]

Now each of the n + 1 values is computed once, so the time drops from exponential to O(n), with O(n) memory for the table (plus recursion depth).

Key idea

Dynamic programming = break a problem into overlapping subproblems, solve each subproblem once, and reuse the stored answer.

When does it apply?

Expert viewRecognising a DP problem

Look for: a question asking for a count, a minimum, a maximum or "is it possible"; choices made step by step; and a way to describe the situation after some choices as a small state (for example "the amount left" or "the first i items and capacity c"). Then write a recurrence that gives the answer for a state from answers to smaller states, name the base cases, and decide the order of evaluation. If subproblems do not overlap (as in merge sort, where pieces are disjoint) memoising gains little; that is plain divide and conquer, covered in part 7. If optimal substructure fails, DP gives wrong answers even though it runs.

Coin change: where the greedy idea fails

You must pay an amount using as few coins as possible. The coin values are 1, 3 and 4, and the amount is 6.

In plain words

Greedy grabs the biggest coin that fits, which feels natural but ignores what remains. DP asks, for every amount from 0 up, "what is the fewest coins for this amount?" and builds on smaller answers.

Text
best[0] = 0
for amount from 1 up to target:
    best[amount] = infinity
    for each coin that is not bigger than amount:
        best[amount] = min(best[amount], 1 + best[amount - coin])
Expert viewCoin change costs

With a target amount n and k coin types this runs in O(n times k) time and O(n) space. Notice it is not polynomial in the number of digits of the amount, so it is fine for moderate amounts. To recover which coins to use, remember the coin that gave each minimum. With standard coin sets, greedy happens to give the optimal answer, but that depends on the set, which is why the 1, 3, 4 case is the classic counterexample.

Knapsack, by intuition

In words: for each item, there are two choices. Leave it, and the best value is whatever the earlier items gave for the same room. Take it, and the best value is its value plus what the earlier items give for the room left after it. Keep the larger. Fill a table with the items down one side and room along the other, and the bottom corner holds the answer.

Expert viewSpace and time for the table

The usual 0/1 knapsack table has (number of items) times (capacity) cells, so O(n times W) time. Because each row depends only on the previous row, you can keep one row and reduce memory to O(W), provided you update the capacities in the right order (from high to low for 0/1 knapsack). The same trick works for many tables, such as coin change (already one-dimensional) and edit distance. Note that O(n times W) depends on the numeric size of W, so knapsack is not known to be solvable in time polynomial in the length of its input; I mention the fact without going further.

Try it by hand

Do not solve the same small problem twice: write the answer down.

Glossary
Recursion
A solution that is defined in terms of smaller copies of the same problem.
Base case
The smallest version of a problem, answered directly.
Call stack
Where a program keeps calls that have started but not finished.
Memoisation
Storing results of calls so repeats are looked up.
Dynamic programming
Solving overlapping subproblems once and reusing the answers.
Subproblem
A smaller version of the problem whose answer helps build the whole.
Recurrence
A formula giving an answer from answers to smaller cases.
Greedy
Always taking the choice that looks best right now.

Frequently asked questions

Is dynamic programming the same as recursion?

No. Recursion is a way of writing a solution. DP is the idea of storing sub-answers; it can be written recursively (top-down) or with loops (bottom-up).

Why is it called dynamic programming?

It is a historical name, and "programming" there means planning or scheduling, not writing code.

Is memoisation always worth it?

Only when subproblems repeat. Otherwise it costs memory and gains nothing.

Does greedy ever work for coin change?

Yes, for some coin sets, such as many everyday currencies, but not for all, as the 1, 3, 4 case shows.

Key takeaways

  • Recursion solves a problem by solving a smaller copy of it
  • Naive recursion can repeat the same work exponentially often
  • Dynamic programming stores sub-answers so each is computed once
