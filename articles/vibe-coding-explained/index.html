Vibe coding explained: what it is, where it works, where it breaks

A balanced, picture-led guide to vibe coding: what the term means, a spectrum from pure vibe to careful AI-assisted engineering, where each fits, the honest limits, a safety checklist and a gate between prototype and production.

Reading level

"Vibe coding" is the name people give to building software by describing what you want to an AI and accepting what it writes, without reading the code closely. It is exciting, useful and often misunderstood. This article is balanced on purpose: what it is, where it works well, where it breaks, and a middle path I actually use. Everything factual is sourced at the end (last checked 2026-10-21). My own opinions are labelled.

In plain words

Vibe coding means steering software by describing it in plain language, running it, and asking for changes, with little or no checking of the code underneath. It is a style of working, not a guarantee of quality.

Where the term comes from

Key idea

The term was introduced by the AI researcher Andrej Karpathy in a post on X on 2 February 2025, according to the encyclopedia entry on the term, which quotes him as describing how you "fully give in to the vibes, embrace exponentials, and forget that the code even exists". I could not open the original post myself, so I am relying on that secondary source for the date and wording. In my own words: it began as a description of a loose, experimental way of working, and it has since become a broad label.

The kitchen analogy

My view and analogy (not from the specification)

My own analogy. Cooking from a recipe you wrote yourself is like traditional coding: slow, but you know every ingredient. Vibe coding is like ordering from a kitchen you cannot see into: you describe the dish, taste it, and ask for more salt. That is fine for a snack. If you are serving a wedding, you want to know what is in the kitchen, how clean it is, and who is responsible when someone gets ill.

The spectrum

What it is genuinely good at

Proven foundation

Anthropic's own best-practice guide for Claude Code says the tool "can read your files, run commands, make changes, and autonomously work through problems", and describes the shift from writing code yourself to describing what you want. The same guide treats checking the result as essential, which is the point of the next sections.

The honest limits

Proven foundation

Claude Code's documentation names this gap directly. It calls it the trust-then-verify gap: "Claude produces a plausible-looking implementation that doesn't handle edge cases", and the fix it gives is "Always provide verification (tests, scripts, screenshots). If you can't verify it, don't ship it." Independent reporting has also raised security and quality concerns about AI-generated code; the encyclopedia entry collects several of them, but I have not verified them myself, so I do not quote figures here.

A safety checklist for vibe coding

Proven foundation

Claude Code's documentation says checkpoints only track changes made through Claude's file editing tools and are not a replacement for git. It also recommends giving Claude a check it can run, such as tests, a build or a screenshot, and exploring and planning before coding for changes that touch several files.

The gate between prototype and production

An example from my own work

My view and analogy (not from the specification)

I want to be clear that my own way of building is not pure vibe coding. I build small Android apps with AI help, and I describe it as AI-assisted engineering. The AI drafts much of the code, but I define the job, review the changes, and rely on checks: automated tests, scripted screen checks on a phone, random-input stress tests, and a pass on a real device before anything is released. The detail of how I work is in How I build small Android apps with AI assistance. On one occasion a slip involving demonstration data was caught by these checks before release, which is exactly the kind of thing a pure vibe approach would have shipped.

Who it is for

Should I vibe code this?

Expert viewVibe coding, agentic coding, and spec-driven development

These words overlap. In my own usage, vibe coding is about attitude: accept the output without reading it. Agentic coding is about tooling: an AI that can read files, run commands and iterate on its own, which Claude Code's documentation calls an agentic coding environment. Spec-driven work writes the requirements first. The best-practice guide describes a version of this: for larger features, have Claude interview you and write a spec to a file, then start a fresh session to implement it. You can be agentic and careful, or agentic and careless.

Expert viewContext, instructions and checks

Claude Code's documentation says most best practices come from one constraint: the context window fills quickly and performance degrades as it fills. Practical consequences it lists: keep a short CLAUDE.md of standing rules, clear context between unrelated tasks, and after two failed corrections start fresh with a better prompt. See CLAUDE.md and memory and Context explained. Write tests first or give the AI an executable check, so it can run it, read the result and iterate.

Expert viewReviewing large AI changes

Split big changes into small ones so each diff can be read. The documentation suggests a fresh session as reviewer, since it is not biased toward code it just wrote, and warns that a reviewer asked to find gaps will usually report some, so tell it to flag only issues that affect correctness or the stated requirements. Read the tests as well as the green result; an agent can make a failing test pass by weakening it. See Part B of the delivery playbook for gates and release.

Expert viewSecurity, cost and team policy

Scan for secrets before every commit, check dependencies you did not choose, validate inputs, and keep authorisation checks reviewed by a person. Watch token use on long sessions; see Tokens explained. Licence and legal questions depend on your country and your employer, so check your own rules rather than assuming. For teams I would write a short policy: what may be vibe coded, what needs review, and who signs off a release. Use Claude Code and AI agents for permissions and safe habits.

Speed is only an advantage when someone checks the destination.

Glossary
Vibe coding
Building software by describing it to an AI and accepting its output with little or no code review.
AI-assisted engineering
Using AI to write code while a person defines, tests and reviews it.
Agentic coding
An AI that can read files, run commands and iterate on its own.
Spec-driven development
Writing the requirements before the code is built.
Prompt injection
Hidden instructions in content that try to steer an AI.
Staged release
Releasing to a small group first, then widening.

Frequently asked questions

Is vibe coding bad?

No. It is a good fit for prototypes and personal tools. The risk comes from treating a prototype as production.

Do I still need to learn to code?

You can start without, but understanding behaviour, data and security is what lets you own the result.

Is AI-assisted engineering just slower vibe coding?

It is a different goal: keep much of the speed, and add the checks that make the result trustworthy.

Where do I begin safely?

Build something small for yourself, use git, ask for tests, and read the diff.

Key takeaways

  • Vibe coding is great for prototypes and personal tools
  • Starting is easy, owning the result still takes understanding
  • Add tests, review and a staged release before anything real depends on it
