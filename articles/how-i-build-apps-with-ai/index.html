How I build small Android apps with AI assistance

A first-person, honest account of designing, building, testing and preparing 24 small offline Android apps with AI tools, what the AI does well, what it does badly, and why a human still reviews everything.

In my own time I design and prepare small Android apps for everyday jobs: shops, homes, families and kids. There are 24 so far, prepared end to end and being readied for Google Play. I use AI-assisted development and agents to build them. This is an honest description of how that works, written for people who are curious, not only for engineers.

The idea: small apps that do one job

Each app does a single, ordinary job. Keeping records for a salon, tracking warranties, helping a child practise times tables, planning household chores. Small scope means each app can be finished, tested and explained in plain words. That is the first design decision, and it is mine, not the AI's.

Design rule one: the data stays on the phone

Every app stores its data on the phone itself. There is no account to create, no server of mine holding your records, no advertising and no analytics. This is a deliberate trade-off: it is simpler and more private, but it means there is no cloud sync, and if you lose your phone and have no backup, the data goes with it. I would rather be upfront about that than hide it.

Designing around privacy from the start also makes the paperwork honest. Each app has a plain privacy policy, and the store's data-safety answers match what the app really does.

My role and the AI's role

  • What I doDecide what to build and for whom. Write the product specification. Set the rules (privacy, no ads, offline). Review every important change. Run the release process. Decide what is good enough.
  • What the AI doesWrites much of the code from my specification. Writes tests. Drafts documentation and store text. Explains unfamiliar errors. Works through repetitive changes across many files quickly.

Think of it as a very fast junior team that never gets tired, and needs clear direction and careful review. The AI does not own the product. I do.

The pipeline: from idea to a release-ready app

Testing is where the quality comes from

AI can write code quickly, and it can write wrong code quickly. So the safety net matters more, not less. Across the apps there are thousands of automated unit tests, scripted checks that tap through the screens on a phone, and stress tests that throw random input at the app to see whether it breaks. Before any release I run a verification pass. None of this is glamorous, and all of it catches problems before users do.

Key idea

The faster code is produced, the more you need tests and review. Speed without checks is just a faster way to ship bugs.

What AI does well

  • Speed on routine work. Screens, forms and repeated patterns appear quickly.
  • Tests. It is good at writing many small tests, including edge cases I might skip.
  • Explaining. When a build fails with a confusing message, it often explains why.
  • Consistency. Applying the same change across many files without getting bored.
  • Documentation. First drafts of guides, checklists and store text.

What AI does badly

  • Judgement about the product. It will build what you ask, including a bad idea. Deciding what is worth building stays human.
  • Confident mistakes. It can state something wrong with total assurance, so important claims need checking.
  • Silent shortcuts. It may make a test pass in a way that hides a problem, so I read the tests too.
  • Platform rules. App store policies and signing details change, and the AI can be out of date. I verify these against the official pages.
  • Knowing when to stop. It sometimes adds more than was asked. Small batches and review keep it in bounds.
Careful

AI-written code is not trustworthy because it looks tidy. I treat every change as untrusted until it has been read and tested.

Tools I use

For building, I use web technology packaged as native apps: React Native with Expo and Capacitor, with local Android builds and app signing. Automation runs through GitHub Actions workflows for Android and iOS builds, and the website is a static site on GitHub Pages. The store side is the Google Play Console, with release tracks, store listings, data-safety and content-rating answers. I also use scripts and the Play developer API to cut repetitive steps.

Learning unfamiliar platforms

Much of this is new ground: app stores, signing, release processes. I am comfortable learning unfamiliar platforms, and the AI is a patient guide. But a guide is not a certificate. When it matters, such as a policy or a deadline, I check the official source myself.

Lessons so far

  1. Write the specification first. Everything downstream improves.
  2. Work in batches, and keep several tracks moving with honest status.
  3. Make privacy a design rule, not a paragraph in the policy.
  4. Invest in tests early.
  5. Review everything that matters, even when it looks perfect.
Glossary
Offline-first
An app that works fully without an internet connection.
Specification
A written description of what to build, before building it.
Unit test
A small automated check of one piece of code.
Signing
Marking an app release as coming from you, so it can be verified.
Release track
A stage in Google Play, such as testing or production, where a version is published.
Agent
AI that works through several steps toward a goal using tools.

Frequently asked questions

Are the apps on Google Play?

They are being prepared for Google Play. Until a store button appears on the apps page, they are not yet live there.

Do you write any code yourself?

I direct the product, review quality and run the release process. The AI writes much of the code, under my specification and review.

Why no cloud sync?

To keep things simple and private. The trade-off is that you manage your own backups.
